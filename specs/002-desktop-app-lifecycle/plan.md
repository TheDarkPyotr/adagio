# Implementation Plan: Desktop App Lifecycle

**Branch**: `002-desktop-app-lifecycle` | **Date**: 2026-05-24 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/002-desktop-app-lifecycle/spec.md`

## Summary

Make the Adagio desktop app fully functional end-to-end: persist account and sync-pair
configuration across restarts (JSON file in the platform config directory), wire the sync
engine to actually run `SyncCycle` on startup and on a schedule via per-pair background
runners, and add a file browser panel that lists local folder contents enriched with
per-file sync status from the journal.

## Technical Context

**Language/Version**: Rust 1.78 (stable, edition 2021); Svelte 5 / TypeScript (frontend)

**Primary Dependencies**: Tauri 2.x, adagio-core (existing), adagio-nextcloud (existing),
serde_json (existing), tokio (existing), tokio-util (cancellation tokens)

**Storage**: JSON config file (`config.json`) in `app_config_dir()`; SQLite journal
(`adagio.db`) for sync history — both already present, config file is new

**Testing**: `cargo test` (unit + integration); Tauri desktop build excluded from headless CI

**Target Platform**: Linux, macOS, Windows (all three CI targets)

**Project Type**: Desktop application (Tauri 2.x shell + Rust backend + Svelte frontend)

**Performance Goals**:
- Config load and all pairs ready within 3 s of cold start
- First sync cycle begins within 5 s of launch
- File browser responds to user navigation within 100 ms

**Constraints**: <100 MB RSS at idle; UI actions complete or show feedback within 100 ms;
credentials MUST NOT appear in `config.json` or any log output

**Scale/Scope**: Typically 1–5 accounts, 1–10 sync pairs, sync folders up to ~10 000 files;
file browser lists one directory level at a time (expand-on-demand)

## Phases

### Phase 1: Setup & Foundational Changes (adagio-core)

Update `SyncPairManager` to store full `SyncPair` structs. Implement `PairRunner` in
`adagio-core/src/cycle/runner.rs`. Extend `DefaultSyncEngine` with `start_pair` /
`stop_pair` / `trigger_pair`. All driven by tests written first (Red-Green-Refactor).

**Deliverable**: `cargo test -p adagio-core` passes; `DefaultSyncEngine::start_pair()` runs
a real `SyncCycle` cycle via `PairRunner`.

### Phase 2: Config Persistence (adagio-desktop)

Implement `crates/adagio-desktop/src/config/mod.rs` with `SavedConfig` structs and
`load_config` / `save_config` functions. Update `AppState::new()` to accept `config_dir`
and load the config on startup. Update `add_account`, `remove_account`, `create_pair`,
`delete_pair` to call `save_config` after mutations.

**Deliverable**: Restart app → accounts and pairs are present; `config.json` on disk matches.

### Phase 3: Engine Wiring (adagio-desktop)

Implement `crates/adagio-desktop/src/lifecycle.rs`. Update Tauri `lib.rs` setup hook to
call `lifecycle::start_engine_for_all_pairs()` after `AppState` is managed. Update
`trigger_sync` to delegate to `engine.trigger_pair()`.

**Deliverable**: App startup triggers a sync cycle for all configured pairs within 5 s.

### Phase 4: File Browser (adagio-desktop + frontend)

Add `list_synced_files` Tauri command in `commands/pair.rs`. Update `Dashboard.svelte`
to render a file browser panel with status badges and a manual sync button.

**Deliverable**: File browser shows files with correct status badges; manual sync triggers
a cycle and updates badges.

## Complexity Tracking

| Decision | Why This Approach | Simpler Alternative Rejected Because |
|----------|-------------------|-------------------------------------|
| PairRunner in adagio-core (not adagio-desktop) | Runner orchestrates SyncCycle, which is pure core logic; desktop shell should not own sync scheduling | Putting runner in desktop would mean core tests can't verify the full cycle runs correctly |
| Separate `config/mod.rs` in adagio-desktop | Config loading is desktop-only concern; keeps state.rs focused | Inline in state.rs would make state.rs a god file |
