Every significant feature in Adagio goes through a structured pipeline using SpecKit slash commands before a line of production code is written. Smaller fixes and documentation changes can skip directly to a branch and PR.

## Feature Workflow

<Steps>
<Step>
**Specify** — run `/speckit-specify` with a natural language description of the feature. This produces `spec.md` with user stories, functional requirements, and acceptance criteria.
</Step>
<Step>
**Clarify** — run `/speckit-clarify` to surface underspecified areas. Up to five targeted questions are asked and their answers are encoded back into the spec before continuing.
</Step>
<Step>
**Plan** — run `/speckit-plan` to generate `plan.md` with the chosen technology, architecture decisions, and a proposed file structure.
</Step>
<Step>
**Tasks** — run `/speckit-tasks` to produce `tasks.md`: a dependency-ordered list of concrete implementation tasks.
</Step>
<Step>
**Implement** — run `/speckit-implement` to execute the task list. Tasks are marked complete as they finish.
</Step>
<Step>
**Commit** — run `/speckit-git-commit` to stage and commit the result with a structured commit message.
</Step>
</Steps>

All design artifacts for feature `NNN` live under:

```
specs/NNN-feature-name/
```

## Branch Naming

Branches follow sequential three-digit numbering:

```
NNN-short-description
```

Examples: `013-e2ee-encryption`, `018-mkdocs-docs-site`, `019-lan-peer`.

<Callout type="tip">
Open the PR as a draft immediately after pushing the first commit. This lets CI run on every subsequent push without waiting for the branch to be marked ready for review.
</Callout>

## Pull Request Process

All of the following must pass before a PR can be merged:

| Check | Command |
|---|---|
| Rust lint | `cargo clippy -- -D warnings` |
| Rust formatting | `cargo fmt --check` |
| Rust tests | `cargo test` |
| Docs build (if docs changed) | `npm run build` inside `docs-site/` |

In addition:

- Write a PR description that explains **why** the change is needed, not just what it does.
- For features that include new or changed public API, storage schema, or cross-crate interfaces, create an ADR before the PR is opened (see below).
- Request review from a maintainer when CI is green.

## Architecture Decision Records

Any decision that affects:

- a public API surface,
- the on-disk storage format (e.g. journal schema changes), or
- a cross-crate interface (e.g. changes to `adagio-ipc` message types)

must be documented as an ADR **before** the implementation PR is opened.

Create the file at:

```
docs/adr/ADR-NNN-short-description.md
```

<Callout type="warning">
ADRs are append-only records. If a previous decision is superseded, write a new ADR that references the old one — do not edit the original.
</Callout>
